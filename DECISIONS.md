# Принятые решения

Сюда записываем решения по проекту: что решили, почему и когда. Новые решения добавляем в конец.

## Р-1. Приложение делаем как PWA
- **Дата:** до v0.2 ТЗ
- **Решение:** веб-приложение (PWA), которое открывается в браузере на компьютере, iPhone и Android и ставится на главный экран как обычное приложение.
- **Почему:** один код для всех устройств, не нужно публиковать приложение в App Store и Google Play.

## Р-2. Приложение работает офлайн
- **Дата:** до v0.2 ТЗ
- **Решение:** все данные сначала сохраняются на устройстве. Когда появляется сеть, данные синхронизируются.
- **Почему:** на объекте интернет есть не всегда (примерно в 70% случаев).

## Р-3. Фото выгружаются на диск вручную
- **Дата:** v0.2 ТЗ
- **Решение:** приложение не загружает фото на Яндекс.Диск само. Пользователь выгружает их вручную, как сейчас. Фото хранятся на телефоне там, откуда их легко забрать в любой момент.
- **Почему:** так проще и надёжнее. Приложение работает как «умный просмотрщик»: берёт фото из папки объекта и показывает их по меткам.
- **Открытый вопрос:** как именно телефон хранит фото (общая папка или кнопка «Экспорт» с папкой/архивом). Ответ даст технический тест.
- **Уточнено 2026-10-28:** выгрузка не обязательно на Яндекс.Диск, а в любую папку. См. Р-13.

## Р-4. У каждого исполнителя свой файл с метками (заменено Р-14)
- **Дата:** до v0.2 ТЗ
- **Решение:** метки (точки, типы фото, комментарии) каждый исполнитель хранит в своём файле. Приложение собирает все файлы в общую картину.
- **Почему:** чтобы исполнители не перезаписывали данные друг друга.

## Р-5. Общее хранилище: Яндекс.Диск компании (заменено Р-13 и Р-15)
- **Дата:** до v0.2 ТЗ
- **Решение:** всё лежит в папке объекта на общем Яндекс.Диске компании. Своего облака нет.
- **Почему:** диск уже используется в работе, а фото объектов конфиденциальны и должны оставаться на корпоративном диске.

## Р-6. Фото снимаются через приложение
- **Дата:** до v0.2 ТЗ
- **Решение:** фото делаются камерой из приложения. Приложение даёт файлу уникальное имя и записывает его в метки.
- **Почему:** веб-приложение не может надёжно узнать имя файла из галереи (IMG_xxxx).

## Р-7. Технологии этапа 1
- **Дата:** 2026-10-28
- **Решение:** Vite + React + TypeScript; PWA через vite-plugin-pwa; данные и фото в IndexedDB через Dexie; PDF открываем через pdf.js; точки храним в процентах от размера листа.
- **Почему:** распространённые и простые в поддержке инструменты, работают офлайн во всех браузерах.

## Р-8. Тестируем сначала на Android
- **Дата:** 2026-10-28
- **Решение:** основной телефон для тестов — Android. iPhone проверяем позже, когда будет доступ.
- **Почему:** Android есть под рукой. Особенности Safari (очистка данных) учитываем заранее через кнопку резервной выгрузки.
- **Проверено (шаг 2):** приложение, установленное на главный экран Android через Chrome, получает постоянное хранение. В браузере без установки было отказано.

## Р-9. Публикация для тестов: GitHub Pages
- **Дата:** 2026-10-28
- **Решение:** код хранится на GitHub, тестовая версия публикуется на GitHub Pages (HTTPS, бесплатно).
- **Почему:** PWA на телефоне работает только по HTTPS. Фото и метки на GitHub не попадают, они остаются на устройстве.
- **Как (шаг 2):** после каждого push в main GitHub Actions сам собирает приложение и публикует его. Адрес: https://pakhomswork-lang.github.io/building-survey/. Тестовая страница шага 0 осталась по адресу .../building-survey/spike/.

## Р-10. Помещение у точки
- **Дата:** 2026-10-28
- **Решение:** помещение можно указать у точки вручную. Если помещения заранее размечены на листе, точка получает помещение автоматически. На этапе 1 помещения не назначаем, но модель данных оставляет для них место.
- **Почему:** назначать помещения пока рано, но позже это не должно требовать переделки.

## Р-11. Тип фото задаётся на серию
- **Дата:** 2026-10-28
- **Решение:** выбранный тип применяется ко всем следующим фото серии. Переключить тип можно в любой момент одним нажатием, и дальше фото пойдут с новым типом.
- **Почему:** так быстрее на объекте: не нужно выбирать тип у каждого снимка.

## Р-12. Проект лежит вне OneDrive
- **Дата:** 2026-10-28
- **Решение:** папка проекта — `C:\Projects\Вайбкодинг`.
- **Почему:** OneDrive тормозит на тысячах служебных файлов (`node_modules`) и может портить репозиторий Git при синхронизации.

## Р-13. Фото хранятся отдельно от данных
- **Дата:** 2026-10-28
- **Решение:** фото лежат на телефоне. Пользователь сам переносит их куда угодно: на компьютер, в сетевую папку, на сервер. Приложение на компьютере читает папку, которую ему указали, и само находит нужные фото по уникальному имени.
- **Почему:** фото тяжёлые, а место хранения может меняться (Яндекс.Диск, локальный сервер). Приложение не должно от него зависеть.

## Р-14. Данные синхронизируются автоматически
- **Дата:** 2026-10-28
- **Решение:** проекты, листы, точки, типы и количество фото, комментарии, участники и настройки хранятся на сервере и синхронизируются сами. Участник подключается к проекту по ссылке и сразу видит готовые листы. Без сети данные копятся на устройстве и отправляются, когда сеть появится. Каждая запись помечена автором, поэтому чужие данные никто не перезаписывает.
- **Почему:** вручную переносить файлы с метками неудобно. Создатель проекта один раз загружает планы, остальные получают их сами.

## Р-15. Где работает сервер: решаем перед этапом 2
- **Дата:** 2026-10-28
- **Решение:** предпочтительный вариант — рабочий компьютер, который не выключается. Кандидат — PocketBase (одна программа: база, вход пользователей, файлы планов) плюс бесплатный туннель с постоянным адресом HTTPS. Запасной вариант — бесплатный облачный тариф (Supabase). Этапу 1 сервер не нужен.
- **Условия:** бесплатно, без сложной настройки, позже можно перенести на сервер компании.
- **Открыто:** разрешает ли IT компании запускать такую программу на рабочем компьютере.
- **Уточнено 2026-11-01:** начинаем с сервера (PocketBase + туннель с постоянным HTTPS-адресом) на личном ноутбуке владельца как тестовом. Потом переносим на рабочий компьютер: у PocketBase это перенос одной папки с данными. Пока ноутбук выключен или спит, телефоны работают офлайн и досылают данные позже.

## Р-16. Что команда видит о чужих фото
- **Дата:** 2026-10-28
- **Решение:** на старте участники видят точки, количество фото каждого типа и автора. Превью фото добавим позже.
- **Почему:** этого хватает, чтобы понять, кто где снимал, и при этом не гонять фото через сервер.

## Р-17. Основной браузер на Android: Chrome
- **Дата:** 2026-10-28
- **Решение:** приложение делаем и проверяем под Chrome. Яндекс Браузер не поддерживаем.
- **Почему:** по тесту шага 0 Chrome сохраняет фото в выбранную папку, а в Яндекс Браузере выбор папки зависает с ошибкой.

## Р-18. Код автора в имени фото
- **Дата:** 2026-10-28
- **Решение:** при первом запуске пользователь вводит имя и короткий код (2–5 латинских букв или цифр, например IVA). Имя фото: `КОД_ГГГГММДД_ЧЧММСС_xxxx.jpg`, например `IVA_20261028_221438_1sr8.jpg`. Внутренние номера записей остаются случайными (UUID).
- **Почему:** по имени файла сразу видно, кто снимал, даже без приложения. Дата вместо счётчика: счётчик начнётся заново после переустановки приложения, и имена повторятся. Латиница — чтобы имена не портились при переносе на другие компьютеры и в архивы. Внутренние номера человек не видит, а случайные гарантированно не совпадут между телефонами.
- **На этап 2:** при подключении к проекту проверять, что код не занят другим участником.

## Р-19. Как хранятся листы
- **Дата:** 2026-10-29
- **Решение:** PDF и фото плана при загрузке превращаются в картинку JPEG, длинная сторона 4096 пикселей. Каждая страница PDF становится отдельным листом с названием «имя файла — стр. N». Для списка делается превью 400 пикселей. Исходный PDF не храним.
- **Почему:** одна картинка открывается быстро на любом телефоне и одинаково выглядит везде. 4096 пикселей хватает, чтобы читать оси и надписи при увеличении, и это в пределах того, что выдерживает iPhone.
- **Проверить:** на настоящих PDF из AutoCAD, хватает ли чёткости мелкого текста.

## Р-20. Встроенная камера и запасная обычная
- **Дата:** 2026-10-29
- **Решение:** основная съёмка идёт встроенной камерой приложения. Камера не закрывается после снимка, тип серии переключается прямо на экране камеры. Пока камера снимает (около 0,7 с), на экране «Держите…», а вспышка и вибрация срабатывают, когда фото готово. Для важных мелких деталей оставлена кнопка «Обычная камера» (системная, с подтверждением снимка).
- **Почему:** по тесту на Android обе камеры дают 12,6 Мп, но обычная лучше обрабатывает снимок. Встроенная заметно быстрее для серий. Смаз во встроенной был из-за того, что вспышка на экране срабатывала раньше самого снимка.
- **Запасной вариант:** снимать обычной камерой и раскладывать фото по точкам по времени съёмки.

## Р-21. Фото сохраняются в выбранную папку телефона
- **Дата:** 2026-10-29
- **Решение:** на экране объекта пользователь один раз выбирает папку на телефоне. Каждое новое фото сразу записывается туда в подпапку с названием объекта: `<папка>/<объект>/MAX_20261029_140512_ab12.jpg`. Если папка не выбрана или браузер забыл разрешение, фото ждут, а на экране объекта появляется кнопка «Сохранить в папку: N фото». Копия фото остаётся и в самом приложении.
- **Почему:** так фото можно забрать на компьютер обычным проводником (Р-13). По тесту шага 0 Chrome на Android умеет писать в выбранную папку.
- **Проверено на Android:** фото сохраняются. Разрешение Chrome держит, пока приложение открыто. После перезапуска приложения при первом открытии камеры Chrome снова спрашивает «Разрешить этому сайту изменять файлы?» (одно нажатие за запуск).

## Р-22. Резервная копия объекта одним архивом
- **Дата:** 2026-11-01
- **Решение:** на экране объекта кнопка «Резервная копия объекта (архив)». В архиве: `data.json` (объект, листы, точки, записи о фото с подписями «лист, точка, тип»), `sheets/01.jpg…` (картинки листов), `photos/<имя>.jpg` (все фото). Архив без сжатия, попадает в «Загрузки».
- **Почему:** защита от потери данных, если телефон или браузер их сотрёт (особенно Safari на iPhone). Архив собирается по одному фото, чтобы телефону хватило памяти на сотни снимков.
- **Пока нет:** восстановления из архива обратно в приложение. Добавим, когда понадобится, или вместе с сервером на этапе 2.

## Р-23. Внешний вид: концепция В «Альбом»
- **Дата:** 2026-11-01
- **Решение:** из трёх черновиков (`design-drafts/`) выбрана концепция В. Светлая серая основа, шрифт Onest. Цвет есть только у типов фото: общий вид серый, дефект красный, замер синий, узел зелёный, вскрытие охра. Метка на плане — кольцо из долей этих цветов, то есть видно, что в точке уже снято. На экране листа сверху план, под ним фото выбранной точки крупной сеткой.
- **Правки владельца:**
  - Экран листа работает в двух режимах. **Обход** (точка не выбрана): план почти на весь экран, видны все метки, внизу большая кнопка «Поставить точку». **Выбрана точка:** план меньше, под ним фото точки, кнопки добавления точки нет; крестик или «Весь план» возвращают к обходу.
  - Когда выбрана точка, внизу две кнопки камеры: большая «Снять» (встроенная, для серий) и маленькая «Обычная» в углу (системная, лучше качество, Р-20).
  - На превью листов (экраны «Объекты» и «Объект») метки — маленькие аккуратные точки, а цвета типов показывает полоска под превью.
- **Черновики всех экранов:** `design-drafts/concept-c-screens.html`, скриншоты в `design-drafts/concept-c-screens/`.
- **Почему:** цвет по типам сразу показывает, что снято, а что нет, и пригодится на этапе 2 («помещения без фото»).

## Р-24. Размер меток на плане зависит от приближения
- **Дата:** 2026-11-01
- **Решение:** когда лист показан целиком или приближен не больше чем в 2,5 раза, метка 22 пикселя (кольцо и номер). При сильном приближении метка растёт и останавливается на 34 пикселях. Числа в начале `src/SheetViewer.tsx` (`MARKER_MIN`, `MARKER_MAX`, `MARKER_GROW_FROM`), их можно подстроить после проверки на объекте.
- **Почему:** при отдалённом плане с большим количеством точек крупные метки закрывали половину чертежа. Когда план приближен, места больше, и крупную метку легче нажать.
- **Ещё:** экран листа работает в двух режимах (Р-23). Обход: план на весь экран, фильтр по типам фото (на плане остаются точки, где есть фото этого типа), кнопки «+» и «−», «Поставить точку». Выбрана точка: план сверху, фото точки сеткой, внизу тип, «Снять» и «Обычная».

## Р-25. Новый вид на всех экранах
- **Дата:** 2026-11-01
- **Решение:** концепция В перенесена на все экраны. «Объекты»: карточки с превью первого листа, числом листов и фото и полоской типов. «Объект»: листы карточками по два в ряд, ниже строки «Все фото объекта», «Папка для фото», «Резервная копия»; «Переименовать» и «Удалить» в меню «…». «Фото объекта»: отбор по листу и типу, фото сгруппированы по точкам. Просмотр фото тёмный, тип меняется цветными кнопками. Встроенная камера: цветные типы, последний снимок слева, «Обычная» справа. Меню точки «…»: комментарий и удаление. В шапке листа можно выбрать другой лист.
- **Убрано:** отдельный экран «фото точки с вкладками»: фото точки уже видны сеткой под планом, нажатие сразу открывает просмотр.
- **Цвет системной полосы Android:** берётся из настроек установленного приложения (`theme_color`), теперь он светло-серый. Chrome обновляет эти настройки у установленного приложения сам, не сразу.

## Р-26. Иконка приложения: «Видоискатель», цвет «Кирпич»
- **Дата:** 2026-11-01
- **Решение:** иконка — рамка видоискателя камеры и трещина в кадре. Фон кирпичный `#9b4a34`, рамка светлая `#f4ece4`, трещина тёмная `#2a1a14`. Исходник `public/icon.svg`, все размеры (Android, iPhone, значок вкладки) делаются командой `npx pwa-assets-generator` по настройкам `pwa-assets.config.ts`. Для Android отступ 18%, чтобы рамку не обрезала круглая маска.
- **Почему:** владелец выбрал из вариантов в `design-drafts/icons*.html`. Видоискатель с трещиной говорит о главном действии — съёмке дефектов; кирпичный цвет из мира стройки и не путается с иконками других приложений.

## Р-27. Синхронизация через Яндекс.Диск вместо своего сервера
- **Дата:** 2026-11-02
- **Решение:** данные бригады синхронизируются через Яндекс.Диск, свой сервер (PocketBase с туннелем на ноутбуке) и PocketHost пока откладываем. В общей папке объекта на Диске у каждого участника свой файл с его данными (например, `points_IVA.json`), рядом картинки листов. Приложение раз в несколько минут, когда есть интернет, записывает свой файл и читает чужие. Каждый пишет только в свой файл, поэтому чужие данные не затираются (Р-14). Вход через Яндекс-аккаунт.
- **Почему:** владельцу сложно держать сервер и туннель, а ноутбук спит. Яндекс.Диск привычен, работает в России и ничего не нужно держать включённым. Сравнение вариантов: `Варианты синхронизации.pdf`.
- **Сначала тест:** страница `public/spike-yandex/` (адрес .../building-survey/spike-yandex/) проверяет с телефона вход, запись и чтение файлов. Запрос с компьютера показал, что API Яндекс.Диска и адрес скачивания пускают запросы из браузера. Загрузку файлов проверит тест.
- **Запасной вариант:** PocketHost (PocketBase на чужом сервере), если тест не пройдёт.
- **Итог теста 02.11.2026 (Chrome на Android):** вход, создание папки, список файлов и запись работают (2 МБ — около 17 с по мобильной сети). Чтение файлов не работает: адрес скачивания `downloader.disk.yandex.ru` не разрешает странице читать ответ (файл доступен, браузер блокирует). В Яндекс Браузере не прошла и запись 2 МБ. Для чтения нужен обходной путь, решаем с владельцем.
- **Итог (03.11.2026):** от Яндекс.Диска отказались: чтение возможно только через посредника в Яндекс Облаке, а регистрироваться там владелец не хочет. Новое решение — Р-28.

## Р-28. Синхронизация через Supabase (бесплатный тариф)
- **Дата:** 2026-11-03
- **Решение:** данные бригады хранятся в Supabase: вход по почте и паролю, таблицы (объекты, листы, точки, записи о фото), хранилище картинок листов, мгновенные обновления на других телефонах. Каждая запись помечена автором; правила базы (RLS) разрешают всем участникам читать, а менять и удалять — только автору (Р-14). Без сети данные копятся на телефоне и досылаются позже. Фото через сервер не идут (Р-13).
- **Почему:** бесплатно, без своего сервера и включённого ноутбука, всё нужное есть в одном сервисе. Бесплатный тариф: база 500 МБ, файлы 1 ГБ (сотни листов), трафик 5 ГБ в месяц, файл до 50 МБ, до 2 проектов. Сайт открывается из России без VPN.

- **Ограничения и риски:** если неделю никто не пользуется проектом, Supabase его усыпляет; будить кнопкой на supabase.com, данные сохраняются. Иностранный сервис: доступ из России могут ограничить. Поэтому резервная копия объекта (Р-22) остаётся, а данные приложения не должны зависеть от Supabase так, чтобы его нельзя было заменить.
- **Сначала тест:** `public/spike-supabase/` (адрес .../building-survey/spike-supabase/) и `supabase/spike.sql` (тестовая таблица и хранилище с правилами). Тест проверяет вход, запись и чтение точек, защиту чужих данных, загрузку и чтение листов 100 КБ–2 МБ, мгновенные обновления.
- **Ключи:** в приложении только publishable key (он публичный, доступ ограничивают правила базы). Secret key никогда не попадает в код.
- **Проект:** `https://rfhkuqboctwgsjdwfgjp.supabase.co`, регион Central EU (Frankfurt), подтверждение почты при регистрации выключено.
- **Итог теста 10.11.2026 (Chrome на Android):** все 15 проверок прошли. Вход, запись, изменение и чтение точек — 0,2–0,6 с. Событие о новой точке приходит через 0,6 с, точка с компьютера пришла на телефон сразу. Листы 100 КБ–2 МБ загружаются и читаются за 0,5–1,7 с. Защита работает: точку от чужого имени и файл в чужую папку сервер не принимает, чужие точки изменить нельзя.
- **Ограничения бесплатного тарифа:** база 500 МБ, файлы 1 ГБ, трафик 5 ГБ в месяц, файл до 50 МБ, 200 одновременных подключений, 2 млн мгновенных сообщений в месяц, 2 активных проекта. Автоматических резервных копий нет. После недели без работы проект засыпает; разбудить можно в течение 90 дней, потом только восстановление из выгрузки.

## Р-30. Таблицы общих объектов на сервере
- **Дата:** 2026-11-11
- **Решение:** скрипт `supabase/02_sync.sql`. Таблицы `projects`, `project_members`, `sheets`, `points`, `photos` (записи о фото, сами фото не идут — Р-13). Хранилище `sheets` для картинок листов: путь `<id объекта>/<id листа>`, только картинки, до 50 МБ.

- **Связи:** точка стоит только на листе своего объекта, фото — только у точки своего листа (сервер проверяет).
- **Уборка теста шага 12:** таблица `spike_points` удаляется скриптом, хранилище `spike` — руками в Storage. Страница `spike-supabase` и `supabase/spike.sql` удалены из кода (остались в истории Git).
- **Исправление (12.11.2026):** первая проверка показала, что автор листа не может загрузить картинку: в правиле хранилища `name` внутри проверки читалось как название листа, а не имя файла. Исправлено на `objects.name` в `02_sync.sql` и отдельным скриптом `supabase/03_fix_sheet_files.sql` (он же убирает записи, оставшиеся от неудачной проверки).
- **Проверка правил:** страница `check-sync/` (адрес .../building-survey/check-sync/) под своим аккаунтом создаёт тестовый объект, проверяет ~25 правил и удаляет всё за собой. Правило про чужие точки на листе проверим в шаге 15, когда появится второй участник.
- **Итог проверки 12.11.2026 (Chrome на Android):** все 26 проверок прошли. Мгновенное событие о новой точке — 0,2–0,5 с.

## Р-32. Отправка общих объектов на сервер
- **Дата:** 2026-11-12
- **Решение:** на экране объекта строка «Работать с бригадой». Нажал → окно с объяснением → «Отправить на сервер». Объект помечается общим (`shared`), и дальше всё, что в нём меняется, уходит на сервер само. Выключить общий режим пока нельзя. Без входа в аккаунт строка подсказывает войти.
- **Автор:** пока вошли, новые записи подписываются id аккаунта (`settings.accountId`), без входа — случайным id телефона. Записи общего объекта с id телефона переподписываются аккаунтом при включении и перед каждой отправкой (в том числе сделанные без входа).
- **Что ждёт отправки:** у записи поле `pushedAt` — какая её правка уже на сервере. Не равно `updatedAt` → ждёт. У листа ещё `imagePushed` — загружена ли картинка. Отправляются только свои записи, по порядку: объект → листы (запись, картинка, путь к картинке) → точки → записи о фото, пачками по 200. Если пачку не приняли, записи идут по одной, чтобы одна плохая не держала остальные. Картинка удалённого листа удаляется из хранилища.
- **Когда:** при входе и запуске, через 1,5 с после любой правки, когда появилась сеть, раз в минуту, если что-то не ушло, и по нажатию на строку.
- **Строка состояния:** «Всё на сервере», «Ждёт сети: N», «Отправляем… осталось N», «Не отправлено: N. <причина>», «Ждёт входа в аккаунт: N». Шаг 14б-3 сделан тут же: без строки отправку на телефоне не проверить.
- **Удаление листа в общем объекте:** чужой лист удалить нельзя («Лист добавил другой участник, удалить может только он»), свой лист с точками других участников — тоже («На листе есть точки других участников»). В окне такие листы не нажимаются.
- **Проверено на телефоне 12.11.2026:** отправка, «Ждёт сети» в режиме полёта и досылка работают.
- **Код:** `src/sync.ts` (отправка), `src/TeamStatus.tsx` (строка и окно), `adoptDeviceRecords` / `shareProject` / `getAuthorId` в `src/db.ts`. Схема базы телефона не менялась: новые поля не участвуют в поиске.

## Р-33. Получение общих объектов с сервера
- **Дата:** 2026-11-12
- **Решение:** пока выполнен вход, телефон забирает с сервера объекты, листы, точки и записи о фото всех объектов, где он участник. Объект появляется в списке сам, картинки листов скачиваются. Сами фото не приходят (Р-13): в просмотре такого фото написано «Фото снято на другом устройстве и хранится там» и имя файла.
- **Как:** сервер помечает записи временем `server_updated_at`. Телефон помнит по каждой таблице, докуда забрал (`settings pull:<таблица>`), и спрашивает только новее, с запасом 2 минуты назад: записи одной пачки имеют одно время, и запас не даёт их потерять. Повторно пришедшая запись ничего не портит. Порядок: объекты → листы → точки → фото. Место запоминается только после того, как всё легло в базу.
- **Когда:** при входе и запуске, сразу после изменения на сервере (мгновенные обновления, подписка на 5 таблиц), при появлении сети, когда приложение снова на экране, после переподключения и раз в 5 минут.
- **Конфликт:** своя правка, которая новее серверной, остаётся и уйдёт на сервер. Иначе берём серверную. Удалённые на другом устройстве лист и фото убираются и тут (картинка листа, файл фото).
- **Другой аккаунт на том же телефоне:** места `pull:*` сбрасываются, его данные забираются с начала.
- **Ограничение:** новый участник объекта (шаг 15) по этому способу не получит старые записи. В шаге 15 при вступлении в объект нужно забрать его целиком.
- **Код:** `src/pull.ts`, запуск в `src/App.tsx` вместе с отправкой.

## Р-36. Сервер не отвечает — не ждать вечно; объекты-«призраки» убирать
- **Дата:** 2026-11-13
- **Что случилось:** (1) коллега на iPhone нажала «Присоединиться» — бесконечная загрузка, после обновления страницы вечное «Проверяем приглашение…». Вероятная причина: связь с Supabase из России без VPN «повисает» (соединение не рвётся, но не отвечает); у владельца на телефоне VPN, у него всё работает. Нужно подтвердить проверкой без VPN. (2) У владельца в списке остались объекты «ТЕСТ проверки…»: их создала и потом стёрла с сервера страница `check-sync`, а телефон про стирание не узнал (получение забирает только изменённые записи, стёртых на сервере нет).
- **Решение:**
  - Каждый запрос к серверу ограничен по времени: 25 с, файлы (картинки листов) — 120 с. Потом понятное сообщение «Сервер не отвечает…» вместо вечной загрузки. Код: `fetchWithTimeout` и `explainNetwork` в `src/supabase.ts`.

Объект, который уже был на сервере, а теперь его там нет, помечается удалённым только в телефоне (на сервер это не уходит), картинки его листов стираются. Перед этим сервер переспрашивается, чтобы не убрать объект, который только что отправили. Код: `dropGhostProjects` в `src/pull.ts`.

## Р-38. Чужие точки и фото в общем объекте
- **Дата:** 2026-11-14

(ИВА)», кнопки «…» (комментарий, удаление) нет — комментарий только читать. В просмотре чужого фото «Снимал: …», нет удаления и смены типа (тип просто показан). Превью чужого фото, которого нет в телефоне, показывает код автора из начала имени файла.
- **Имена:** телефон после каждого получения забирает имена и коды участников своих общих объектов (`profiles`) и хранит в `settings person:<id>`, чтобы видеть их и без сети. Код: `src/people.ts` (`refreshPeople`, `usePeople`).

## Р-39. Приложение на компьютере (шаг 17)
- **Дата:** 2026-11-14
- **Решение владельца:**
  1. На компьютере тот же сайт в Chrome, установленный кнопкой «Установить приложение». Главное — скорость «как в проводнике». Если сайт окажется медленным, после готовности вернёмся к вопросу о настоящей программе.
  2. У объекта на компьютере одна папка «Фото», туда вся бригада выгружает фото как удобно. Приложение ищет фото по имени в этой папке и во всех вложенных.
  3. Точки на компьютере не ставим. Нужно: менять тип фото и удобно отбирать фото сразу по нескольким признакам (лист, тип, автор, а потом конструкции и помещения — отборов станет больше).
  4. «Сортировщик для заключения» — это быстрый отбор плюс выгрузка описания всех фото (что за фото, где снято) для ИИ.
  5. Фото, которых нет в папке: достаточно понятно показать, у кого сколько не найдено.
  6. Три способа смотреть: план с точками и фильтрами (найти конкретное фото в конкретном месте); миниатюры с фильтрами без плана (просмотреть, например, все общие виды или все замеры); просто все фото подряд.
- **Как сделано (17а):** папка объекта на компьютере запоминается отдельно от папки телефона (`folders`, ключ `pc:<id объекта>`), только чтение. Приложение обходит папку со всеми вложенными и запоминает, где лежит каждое фото. Миниатюры делаются из фото один раз и хранятся в новой таблице `folderThumbs` (`db.version(3)`), потом открываются сразу. На компьютере (мышь вместо пальца) вместо строки «Папка для фото» — «Папка с фото на компьютере». Код: `src/pcFolder.ts`, `src/PcFolderStatus.tsx`.

## Р-40. Отдельная версия для компьютера
- **Дата:** 2026-11-14
- **Что случилось:** владелец открыл 17а на компьютере. Сайт сделан под телефон: кнопки «Снять» и «Поставить точку» не нужны, лист двигается неудобно (после правой кнопки всплывает меню браузера и лист перестаёт двигаться), лист на большом мониторе нечёткий (картинка 4096 точек, Р-19).
- **Решение владельца:** отдельная версия для компьютера по своему адресу `…/building-survey/pc/`. Тот же сайт и те же данные (вход, объекты с сервера, папка с фото), но свои экраны под большой монитор и мышь. Точки, фото и листы в ней не добавляют. Устанавливается отдельно как «Обследование — компьютер». Телефонную версию не трогаем.
- **План (шаг 17):** 17б-1 каркас (адрес, вход, объекты, экран объекта); 17б-2 лист под мышь (колесо — приближение к курсору, левая кнопка — тащить, без меню браузера) и фото точки справа; 17б-3 сетка фото с несколькими отборами и три вида просмотра, смена типа фото; 17б-4 чёткие листы — на компьютере к листу можно указать исходный PDF, лист рисуется из него (только на этом компьютере).
- **Код:** вход `pc/index.html`, экраны в `src/pc/`.
