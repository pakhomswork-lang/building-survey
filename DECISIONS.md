# Принятые решения

Сюда записываем решения по проекту: что решили, почему и когда. Новые решения добавляем в конец.

## Р-1. Приложение делаем как PWA
- **Дата:** до v0.2 ТЗ
- **Решение:** веб-приложение (PWA), которое открывается в браузере на компьютере, iPhone и Android и ставится на главный экран как обычное приложение.
- **Почему:** один код для всех устройств, не нужно публиковать приложение в App Store и Google Play.

## Р-2. Приложение работает офлайн
- **Дата:** до v0.2 ТЗ
- **Решение:** все данные сначала сохраняются на устройстве. Когда появляется сеть, данные синхронизируются.
- **Почему:** на объекте интернет есть не всегда (примерно в 70% случаев).

## Р-3. Фото выгружаются на диск вручную
- **Дата:** v0.2 ТЗ
- **Решение:** приложение не загружает фото на Яндекс.Диск само. Пользователь выгружает их вручную, как сейчас. Фото хранятся на телефоне там, откуда их легко забрать в любой момент.
- **Почему:** так проще и надёжнее. Приложение работает как «умный просмотрщик»: берёт фото из папки объекта и показывает их по меткам.
- **Открытый вопрос:** как именно телефон хранит фото (общая папка или кнопка «Экспорт» с папкой/архивом). Ответ даст технический тест.
- **Уточнено 2026-10-28:** выгрузка не обязательно на Яндекс.Диск, а в любую папку. См. Р-13.

## Р-4. У каждого исполнителя свой файл с метками (заменено Р-14)
- **Дата:** до v0.2 ТЗ
- **Решение:** метки (точки, типы фото, комментарии) каждый исполнитель хранит в своём файле. Приложение собирает все файлы в общую картину.
- **Почему:** чтобы исполнители не перезаписывали данные друг друга.

## Р-5. Общее хранилище: Яндекс.Диск компании (заменено Р-13 и Р-15)
- **Дата:** до v0.2 ТЗ
- **Решение:** всё лежит в папке объекта на общем Яндекс.Диске компании. Своего облака нет.
- **Почему:** диск уже используется в работе, а фото объектов конфиденциальны и должны оставаться на корпоративном диске.

## Р-6. Фото снимаются через приложение
- **Дата:** до v0.2 ТЗ
- **Решение:** фото делаются камерой из приложения. Приложение даёт файлу уникальное имя и записывает его в метки.
- **Почему:** веб-приложение не может надёжно узнать имя файла из галереи (IMG_xxxx).

## Р-7. Технологии этапа 1
- **Дата:** 2026-10-28
- **Решение:** Vite + React + TypeScript; PWA через vite-plugin-pwa; данные и фото в IndexedDB через Dexie; PDF открываем через pdf.js; точки храним в процентах от размера листа.
- **Почему:** распространённые и простые в поддержке инструменты, работают офлайн во всех браузерах.

## Р-8. Тестируем сначала на Android
- **Дата:** 2026-10-28
- **Решение:** основной телефон для тестов — Android. iPhone проверяем позже, когда будет доступ.
- **Почему:** Android есть под рукой. Особенности Safari (очистка данных) учитываем заранее через кнопку резервной выгрузки.

## Р-9. Публикация для тестов: GitHub Pages
- **Дата:** 2026-10-28
- **Решение:** код хранится на GitHub, тестовая версия публикуется на GitHub Pages (HTTPS, бесплатно).
- **Почему:** PWA на телефоне работает только по HTTPS. Фото и метки на GitHub не попадают, они остаются на устройстве.

## Р-10. Помещение у точки
- **Дата:** 2026-10-28
- **Решение:** помещение можно указать у точки вручную. Если помещения заранее размечены на листе, точка получает помещение автоматически. На этапе 1 помещения не назначаем, но модель данных оставляет для них место.
- **Почему:** назначать помещения пока рано, но позже это не должно требовать переделки.

## Р-11. Тип фото задаётся на серию
- **Дата:** 2026-10-28
- **Решение:** выбранный тип применяется ко всем следующим фото серии. Переключить тип можно в любой момент одним нажатием, и дальше фото пойдут с новым типом.
- **Почему:** так быстрее на объекте: не нужно выбирать тип у каждого снимка.

## Р-12. Проект лежит вне OneDrive
- **Дата:** 2026-10-28
- **Решение:** папка проекта — `C:\Projects\Вайбкодинг`.
- **Почему:** OneDrive тормозит на тысячах служебных файлов (`node_modules`) и может портить репозиторий Git при синхронизации.

## Р-13. Фото хранятся отдельно от данных
- **Дата:** 2026-10-28
- **Решение:** фото лежат на телефоне. Пользователь сам переносит их куда угодно: на компьютер, в сетевую папку, на сервер. Приложение на компьютере читает папку, которую ему указали, и само находит нужные фото по уникальному имени.
- **Почему:** фото тяжёлые, а место хранения может меняться (Яндекс.Диск, локальный сервер). Приложение не должно от него зависеть.

## Р-14. Данные синхронизируются автоматически
- **Дата:** 2026-10-28
- **Решение:** проекты, листы, точки, типы и количество фото, комментарии, участники и настройки хранятся на сервере и синхронизируются сами. Участник подключается к проекту по ссылке и сразу видит готовые листы. Без сети данные копятся на устройстве и отправляются, когда сеть появится. Каждая запись помечена автором, поэтому чужие данные никто не перезаписывает.
- **Почему:** вручную переносить файлы с метками неудобно. Создатель проекта один раз загружает планы, остальные получают их сами.

## Р-15. Где работает сервер: решаем перед этапом 2
- **Дата:** 2026-10-28
- **Решение:** предпочтительный вариант — рабочий компьютер, который не выключается. Кандидат — PocketBase (одна программа: база, вход пользователей, файлы планов) плюс бесплатный туннель с постоянным адресом HTTPS. Запасной вариант — бесплатный облачный тариф (Supabase). Этапу 1 сервер не нужен.
- **Условия:** бесплатно, без сложной настройки, позже можно перенести на сервер компании.
- **Открыто:** разрешает ли IT компании запускать такую программу на рабочем компьютере.

## Р-16. Что команда видит о чужих фото
- **Дата:** 2026-10-28
- **Решение:** на старте участники видят точки, количество фото каждого типа и автора. Превью фото добавим позже.
- **Почему:** этого хватает, чтобы понять, кто где снимал, и при этом не гонять фото через сервер.

## Р-17. Основной браузер на Android: Chrome
- **Дата:** 2026-10-28
- **Решение:** приложение делаем и проверяем под Chrome. Яндекс Браузер не поддерживаем.
- **Почему:** по тесту шага 0 Chrome сохраняет фото в выбранную папку, а в Яндекс Браузере выбор папки зависает с ошибкой.
